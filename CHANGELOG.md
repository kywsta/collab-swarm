# Changelog

## 0.2.0

- **Installable from a Git tag.** The package is not on npm yet, and `dist/` is not committed, so installing it from GitHub gave a package with no CLI. A `prepare` script now builds it on install, which also covers `npm pack` and `npm publish`: `npm install -D github:kywsta/collab-swarm#v0.2.0`.
- **Changed requirements are traced to the work they reach.** A new BRD version or a change request used to mean re-reading the whole backlog by hand, and a plan already in flight could be finished against requirements nobody wanted any more without anything noticing.
  - **`npx collab-swarm impact`.** Diffs the sources since the delivery plan was last committed (or `--since <ref>`), finds the heading each changed line falls under, and matches those against every row's `Sources` cell. It sorts the rows it reaches into delivered, in progress and not started, sets apart rows that cite a changed document but none of its changed sections, and lists the changes no row cites. A citation may be a path, a file name or a document id (`PRD-02`, `PRD 2`), with `§7.4`, `#anchor` or a quoted heading; one that no longer resolves is reported. `--json` for agents. Read-only.
  - **`sources_sha` in `plan.yml`.** The commit whose sources a plan's requirements were read from. `claim` and `plan` set it to where the plan starts; `deliver-change` sets it again whenever it writes or revises the requirements. `impact` lists every plan in flight whose cited sources have since changed on the default branch, and `validate` warns on the plan itself, so its holder hears about it on resume rather than at review. `validate` asks for it on an unfinished plan that has requirements but none, and rejects one that is not a SHA.
  - **`validate` reports a dependency that can never be done.** A `Depends on` slug that is no row, no plan and nothing the history delivered — a misspelling, or a row deleted during a reconciliation — kept the row naming it blocked for good, with the board saying only that it "is not done". A dependency on a row the history records as dropped is reported too.
  - `to-backlog` reconciles from the impact: a delivered row stays done and gets a follow-up row, an in-flight one is revised through its plan, an unstarted one is reworked or retired, and a business document no row cites is absorbed into the product documents first. `deliver-change` revises a drifted plan from the changed sections before continuing. The workflow contract says all of it once, under *When the sources change*.

- **Rule sets: each repository's conventions, researched from its own code.** Packs exist for few stacks, so a workflow that leaned on them left most projects — and every polyglot hub — implementing from each agent's priors. Each repository now gets a **rule set** in `.collab-swarm/rules/<name>/` (`root` for this repository): a `STACK.md` profile and path-scoped rules, with skills only where a concern's work has an order a rule cannot hold. Rule sets live in the hub, so the team's knowledge stays in one place.
  - **`to-rules` researches it.** It reads the repository — manifests and the exact versions in its lockfile, its tooling and CI, the agent instructions it already carries, and features built end to end — then the official guidance for those versions. It proposes each rule with its evidence, asks the user wherever best practice contradicts the code, and writes only what was agreed. It replaces `to-pack`; `pack new` stays for authoring a pack to share across projects.
  - **Researched again as the code grows.** `npx collab-swarm rules` compares every repository with what its last research recorded (`rules <name> --record` writes `research.json`) and reports packages added, removed or moved a major version, and rules whose globs match no file, putting the stale sets — the ones misleading agents — first. `doctor` reports them too.
  - **Scoped to their repository.** Globs are written relative to the repository; `sync` adds its path, renames each rule after it, and confines a rule with no globs to that repository. A coordinated repository's stack profile is published as a rule that loads only for its files. The instruction block's repositories table names each one's rule set.
  - **Who wrote a rule is recorded.** `origin: research` or `origin: team`; a later pass revises its own rules and only proposes changes to the team's. `validate` rejects an unknown origin, warns on a glob that repeats the repository's path or a rule set belonging to no repository, and reports two sources publishing the same skill or rule instead of letting load order silently drop one.
- **Packs are optional baselines.** `init` attaches none and no longer asks; `--pack <name>` still attaches a default pack when asked. `add <pack> --repo <name>` and `pack options <pack> --repo <name>` attach a pack to one repository, with its own answers and checks, so two apps on the same stack may answer differently. A rule in a repository's rule set replaces the baseline's rule of the same name. `doctor` no longer warns that a project has no pack.

- **A hub can coordinate code repositories.** Some programmes keep their knowledge apart from their code: one repository holds the requirements, the backlog and the plans, and each app is a repository of its own — usually a submodule — with its own remote, default branch, CI and deployment. collab-swarm assumed a feature's plan, claim branch and code all lived in one repository, so in a hub a plan could read as done while its code was still unmerged, and nothing tied the hub's branch to the code branches. `repositories:` in `collab-swarm.yml` now lists the code repositories, each with its path, the branch it merges into, and its own checks; `init` offers a hub's submodules, with the default branch each one's remote advertises and checks detected from each one's own stack.
  - **One branch name everywhere.** `claim` reads a `Repositories` column from the backlog row, pushes `feat/<slug>` in each named repository from its default branch without touching its checkout, and records where each branch started as that repository's `base_sha` in `plan.yml` — its review base, as `implementation_base_sha` is the hub's. `npx collab-swarm repos <slug> --open <name>` adds a repository the specification discovers later; `repos` alone lists the repositories and whether each is checked out.
  - **Done needs the code merged.** A row is done only when its plan is complete on the hub's default branch *and* its branch has merged in every repository the plan names. Until then the board shows it awaiting merge, with the commits still outstanding, and keeps everything depending on it blocked. A branch deleted after merging still counts when the merge commit names it. A repository that is not checked out cannot be confirmed, so it never counts as merged by default. `history` holds such a plan back from compaction, which would otherwise mark the row done early.
  - **Tickets are built in one repository.** A ticket names it with `repository:` whenever the plan lists more than one; `validate` rejects an unknown or missing one, a plan naming a repository nobody configured, a backlog row doing the same, and a repository with no base from the implementation stage onward. A recorded small change may name its repository too.
  - **Checks run where the code is.** Each repository's checks run from its own directory. `check --focus repositories/api/tests/SignInTest.php` runs only that repository's checks with the path made relative to it, `--repo api` names it outright, and the full set skips — and says so — a repository not checked out here.
  - The instruction block in `AGENTS.md` and `CLAUDE.md` lists the repositories and how a feature reaches them, and `deliver-change`, `implement`, `code-review`, `to-spec`, `to-tickets`, `whats-next`, `to-backlog` and `small-change` each handle a hub. `doctor` reports a repository that is not checked out or whose default branch does not exist.
- **`init` detects Laravel, and offers `npm test` only when there is a test script.** A Laravel application carries a `package.json` for its assets and was configured as a Node project; it now gets Pint and `php artisan test`. A Node package with no `test` script no longer gets a check that fails on every run.

- **`compact-history`: finished work, folded into one short file.** Every delivered feature left a plan directory behind, and after a few milestones the plans still in flight were buried under spent tickets and under requirements for features since rebuilt, which still read as true to an agent searching for how something works. `compact-history` turns them into `<plans>/HISTORY.md`: one row per compacted plan or recorded small change, with its status (`delivered`, `superseded`, `dropped`), a one-line note, and the commit that still holds every file of it. Before anything is deleted it judges what the plans cannot say for themselves: which ones a later plan superseded, which specification decisions still constrain the code (promoted to the architecture decisions), which product facts no source holds yet, and which deferred tickets must become backlog rows instead of vanishing. It proposes all of it in one message and acts only on what the user agrees to. It also retires delivered milestones, closed gates and answered questions from the backlog, when nothing unfinished still names them.
- **The board reads the history.** A `delivered` or `superseded` row in `HISTORY.md` on the default branch is done, exactly as a complete plan there was, so a row depending on a compacted feature stays unblocked after its directory is gone; a question retired into the history's settled-questions table stays answered. `claim` says a compacted row is done and where it went.
- **`npx collab-swarm history`.** The facts compacting needs, the same way every time: the history's rows, a verdict for every directory under the plans — ready, still owed deferred work, never finished and untouched for weeks, not yet on the default branch, or live — with the exact commit a history row should name, and the milestones, gates and questions the backlog can retire. A row whose commit cannot give its plan back is reported and fails the command. `--json` for agents. Read-only: it never deletes anything.
- **`validate` checks the history.** Every row needs a slug, a known status and a commit; a slug both compacted and still present as a directory is an error, and a superseded row that does not name its replacement is a warning.

- **`small-change`: a fix without a feature plan.** A one-line fix had two paths, both wrong: a full requirements, specification and tickets plan, or no contract at all — and with no contract, `code-review`'s Feature reviewer had nothing to judge the diff against and quietly fell back to a standards review. `small-change` takes a request that fits one ticket, adds no unsourced behaviour, and continues no open plan; it states a short contract (what changes, why, named acceptance criteria, out of scope, tests), and **asks the user every time whether to record it**. Recorded, it is one `<plans>/<slug>/change.md` that `validate` checks and a later session can resume; unrecorded, it lives in the conversation and the commit message. Either way it is built test-first, reviewed on both axes with the contract as the Feature axis, and stays off the delivery board. Anything that turns out bigger is handed to `deliver-change` or `new-feature`, and the golden rule is now "no contract, no code" rather than "no plan, no code".

- **A claimed session names itself after the feature.** Every session opened through `whats-next` kept the question that started it, so a developer with six of them open had six variations of "What's next?" and no way to tell which held the work they wanted. `whats-next` now renames the session on a successful claim, to the row's title in plain names and nothing that moves — no stage, no lane, no id. The convention is in the workflow contract; a host with no way to title a session skips it silently, since the name is a convenience for the human's list and never what records the claim.

- **A source can be owned, not just read.** The same `api:` contract means opposite things on each side of the wire: an app reads it, so an operation it lacks is a gate another team closes; a service defines it, so the same gap is the work. Everything downstream assumed the first reading, which sent a backend feature off to wait for its own endpoint behind a gate nobody could close. `owned: true` on a source now says this repository defines that contract, and `to-requirements`, `deliver-change`, `to-backlog` and `new-feature` each branch on it: the missing operation becomes a ticket instead of a gate, and the contract file must carry it before the plan completes. `init` asks once per contract source it finds (`--owns api,design` where there is no terminal), and a project still declares only the kinds it has — a service with nothing to render declares no design source and lists its operations and events as its interfaces. `validate` warns when the flag lands on a register the project writes either way (`product`, `domain`, `decisions`), where nothing branches on it; a contract kind a project invents for itself, such as `events`, keeps both readings.

- **`new-feature`: shaping before planning.** A capability asked for in conversation has no source document, so a plan written from it invents the behaviour. The skill researches what the codebase already does, interviews the user in batches until outcome, states and boundaries are settled, confirms the whole thing back in prose, writes it into the project's own product, design and API documents, and hands the rows to `to-backlog`. It starts by sizing the request: a change to behaviour a document already describes — move the control, fix the defect, add the field — goes straight to `deliver-change` instead.
- **`to-backlog`: the delivery plan, written from the documents.** Milestones, the feature register, the human gates and the decisions register, produced from the project's sources and the code already in the repository. Rows are cut as vertical outcomes, ordered by real prerequisites, then arranged so each lane owns a chain and every lane has work on day one of every milestone; cross-lane hand-offs are counted and named, and shared files get one owning lane. Gates carry an owner and a status the board reads, and a gate that can be planned around says so instead of saying `open`. The format reference beside the skill documents what the register parser requires, so a hand-written backlog and a generated one are the same file.

- **The documented command is `npx collab-swarm`.** The package installs three bins — `collab-swarm`, `swarm` and `cswarm` — and every generated document, hint and usage line now names the first. `npx swarm` resolves an *unrelated* package on the npm registry for anyone without a local install, so it was never safe to put in a file an agent reads in a fresh container. Somebody who has installed it can still type `swarm`; nothing tells them to. Usage lines follow whichever bin was invoked, and `steps` still reads `npx swarm` out of a pack written against the old name.
- **Default packs, starting with Flutter.** `npx collab-swarm add flutter` attaches a written-and-tested pack that ships inside collab-swarm — no install step, version-locked to the CLI. It covers a Flutter app end to end: a concern router, ten concern skills (API and data stack, Riverpod state, dependency injection, failures, UI, navigation, storage, observability, push, localization), a screen review, an architecture reference, path-scoped rules for each, and the `generate` check they need. `npx collab-swarm pack list` shows what ships; `npx collab-swarm rules` suggests the one whose marker files a repository holds, as a baseline it may choose.
- **A pack can ask questions.** A stack has a fixed core and a handful of slots every team fills differently. A pack declares those as `options`; `add` and `init` ask them once, and the answers are recorded in `collab-swarm.yml` so a teammate's `sync` reproduces the same files without another interview. Three mechanisms use an answer: `if` decides whether a skill, rule, check or package exists at all; `<!-- swarm:if -->` blocks and inline spans decide the prose; `{{option.var}}` decides the identifiers. `npx collab-swarm pack options <pack>` re-answers them and re-applies everything they decide — a skill an answer rules out is removed from every target, not left behind. The Flutter pack asks seven: push, analytics, crash reporting, logging, local database, localization, and environment configuration.
- **A pack can declare its stack.** `stack` in the manifest carries the architecture summary, the project layout, the conventions that hold everywhere, and the libraries the stack is built on — joined with the packages the chosen options bring in. It is rendered into `AGENTS.md` and `CLAUDE.md`, so an agent reads it before it decides which skill to open, and reaches for a library the project already has instead of adding one. Nothing is written to the project's dependency manifest.
- **`validate` reports an unresolved pack variable or an unclosed conditional.** Both publish into the agent files verbatim, so both are errors rather than something to notice later. `doctor` reports an answer a pack no longer offers, and an option nothing answered.
- **Two new skill roles.** `router` selects the smallest applicable concern set for each red-green slice, so a ticket touching one concern loads one skill rather than the whole pack; `implement` uses it when a pack ships one. `review` reviews a surface a diff cannot judge, and `deliver-change` runs every one at feature review. Neither may be named in a ticket's `skills` — only `ticket` may, as before.
- **`validate` reports a skill with no description and a rule with no `paths`.** The first is never opened by an agent; the second is loaded into every turn. Both were previously silent.
- **`npx collab-swarm steps`.** The installed skills, read back as an execution map: the sequence each one runs, what finishes each step, which skill it hands work to, which `swarm` commands and plan files it touches, and which rules are in force while it runs. `steps <skill>` opens one in full; `steps --rules` inverts the view to show every step a rule governs and the file that brought it into force. Derived from the payload in the checkout — nothing is recorded, and the workflow still keeps no event log.
- The CLI command is now `swarm` (was `collab-swarm`). The npm package, config files, and GitHub repository remain `collab-swarm`. The `cswarm` alias is unchanged.

## 0.1.0

First release. Extracted from the agentic delivery workflow built and used to deliver apps in production, and generalised away from Flutter.

- **Workflow.** `requirements → specification → tickets → implementation → review → complete`, one plan per feature, committed to the repository.
- **Delivery board.** A Markdown feature register joined with Git claims: a pushed branch claims a row, a completed plan on the default branch marks it done, and dependencies, human gates and product decisions derive the blocked state.
- **Validator.** Plan shape, required sections, unfilled template text, ticket front matter, dependency cycles, status coherence, and ticket skills checked against the installed packs.
- **Check runner.** One configured command set that a human, an agent and CI all run, with focused and CI variants.
- **Targets.** Claude Code, the AGENTS.md standard, OpenAI Codex, Cursor, OpenCode and Google Antigravity, chosen at `init`. Targets sharing a directory share one copy of the payload.
- **Packs.** Language and framework skills, rules and checks added after the fact, with roles that decide how each skill may be reached.
- **Sync.** Vendored payload with a manifest, so an upgrade rewrites what it owns, reports what you edited, and removes what an older version left behind.
